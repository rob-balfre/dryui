# Variant D Agentic Gated Output

## 1. Target Brief

Target brief: type=page, subtype=dashboard, user=product analyst, primary_task=monitor analytics performance and drill into recent campaign rows, density=standard with compact table behavior, required_states=loading empty error disabled dense-data.

## 2. Three Variant Summaries With Scores

These were generated by three parallel subagents using `variant-d-agentic-gated/SKILL.md`.

### Structure Variant

Best for information architecture. It defines a task-first page order: header, filters, status, metrics, chart, insights, table. Mobile stays one column. Tablet uses two-column metrics while keeping chart and table full-width. Desktop uses a 12-column grid with chart dominant and insights as a right rail.

Main risk: the insights rail can distract if overbuilt.

### Density Variant

Best for dashboard scan speed. It suggests compact metrics, tighter chart/table comparison, and dense table behavior. It avoids full-width KPI bands on desktop and pushes toward a real work surface.

Main risk: it can become cramped on tablet and mobile if labels and tables are long.

### State/Resilience Variant

Best for state stability. It keeps loading, empty, error, disabled, dense rows, long labels, and no-overflow behavior inside stable page regions. It reinforces the page-shell container rule and inner responsive grid.

Main risk: if all states are rendered at once, the page becomes a state catalogue rather than a realistic dashboard.

## 3. Winning/Merged Implementation Plan

Winner: merge **Structure** and **State/resilience**, with density guidance from the Density variant for the table and KPI treatment.

Implementation plan:

1. Build one full-page Svelte route titled "Analytics Dashboard".
2. Use `main[data-layout="analytics-dashboard-shell"]` as the page shell and named container owner.
3. Put the responsive grid on the inner `section[data-layout-area="page"]`.
4. Use `@container analytics-dashboard (...)` rules to style descendants inside the shell, never the shell itself.
5. Keep the mobile base layout single-column: header, filters, status, metrics, chart, insights, table.
6. At tablet width, use two-column metric layout while keeping chart and table full-width for readability.
7. At desktop width, use a 12-column page grid: metrics across the top, chart dominant, insights rail on the right, table full-width below.
8. Use `Table` or `DataGrid` for tabular data and `Chart` or `Sparkline` for visualized data after checking actual component metadata.
9. Use cards only for KPIs, alerts, or distinct comparable units.
10. Model states as branches inside stable regions: loading skeletons, empty panels, error/retry status, disabled actions, and dense table rows.

## 4. Proposed Svelte Markup Structure

	const hasError = $derived(state === 'error');
	const isEmpty = $derived(state === 'empty');

## 6. Visual Check Plan

Mobile, 390px:

- First viewport shows title, primary actions, and filters without horizontal overflow.
- Metrics stack into one column and long labels wrap without clipping.
- Chart, empty, loading, and error states keep stable spacing.
- Dense table scrolls inside `table-scroll`, not the page.

Tablet, 820px:

- Metrics become two columns.
- Page is not just a stretched phone layout.
- Chart remains full-width so the visualization is not cramped.
- State banners span the content area.

Desktop, 1440px:

- Metrics become four columns.
- Chart owns the dominant left region.
- Insights occupy the right rail without competing with chart.
- Table spans the page below chart/insights.
- Disabled buttons, loading skeletons, empty state, error state, and dense-data table preserve the same grid structure.

Theme:

- If adaptive theme is enabled in the host app, check light and dark. Otherwise keep the concept light-only and avoid theme-specific assumptions.
